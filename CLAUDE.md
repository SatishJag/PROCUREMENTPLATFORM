# CLAUDE.md: Procurement Platform

Source-to-Pay platform for capital projects (data centres, construction), plus construction Accounts Payable. Spec: `PRocurement Platorm.txt`; references `TruBuild.pdf`, `Procure.AI.pptx`. This file is the source of truth for how we build. Keep it current and short (see Upkeep).

## Commands
`npm test` · `npm run typecheck` · `npm run demo` · `npm run api` → http://127.0.0.1:8787/api · web: `npm --prefix web run dev|build` (setup `npm i --legacy-peer-deps` in `web/`). Node ≥22.18 runs `.ts` directly (no build for `server/`, `sample/`). The core is zero-dependency; this product adds `@anthropic-ai/sdk` (for `insight`) and the web toolchain.

## Architecture: modular monolith
```
core + modules/  live in SatishJag/Procurement_core (@satishjag/procurement-core, compiled .js committed, git dependency pinned by commit)
server/  HTTP RPC over each module's `commands`; also serves web/dist
sample/  fictional DC1 seed + demo.ts (DEMO_STAGE states)
test/    flow, server (module tests live in the core repo)
web/     React app (screens per module under web/src/screens/<module>/)
db/      target Postgres DDL for payables (plain SQL, NOT wired in); `node db/verify.mjs` with PGlite via $PGLITE
.claude/ agents/ (the team), skills/ (ponytail, ponytail-review, scroll-craft)
```
Core layout: `kernel.ts` (Platform: table(), clock, id(), emit/on), `types.ts`, `workflow.ts` (Flow, next, guard, available), `audit.ts`, `csv.ts`, `dates.ts`; one `modules/<x>.ts` per capability, `index.ts` = registry + `createPlatform` event wiring.
- **New capability** = `modules/<x>.ts` + `test/<x>.test.ts` + one export line in `index.ts`. Never edit the kernel to add a table or a role (use existing roles).
- **Module talk**: reads via another module's exports, reactions via events (`p.on`). Imports acyclic: intake→planning; sourcing→intake, suppliers; evaluation→sourcing; awards→evaluation, sourcing, intake; payables→sourcing (`projectOf`); insight→evaluation, intake, sourcing; reporting reads all. `insight` is async and advisory (plain role guards, no Flow). Modules never import `server/` or `web/`.
- **Every state change**: `guard` → validate → `next(flow)` → mutate → `p.emit(user,'entity.past_tense',id,data)` (writes the hash-chained audit trail and publishes the event).
- **API** = each module's `export const commands`; pure helpers are unreachable. `POST /api/<module>/<command>` body `{"args":[...]}`, header `x-user-id` → `{ok:true,data}` or `400/401/404/413 {ok:false,error}`. `GET /api` lists commands. Modules with a workflow have an `actions` command (intake, suppliers, sourcing, awards, payables).
- **Swap points** (`ponytail:`): in-memory Maps → Postgres (`kernel.table`; schema in `db/`); sync bus → outbox + Service Bus; `x-user-id` → Entra ID; keyword classifier → LLM.

### Events
intake `requisition.submitted/approved/rejected`, `package.created`, `boq.uploaded` · suppliers `supplier.registered/qualified/rejected/suspended` · sourcing `event.created/published/closed`, `clarification.asked/answered`, `addendum.issued`, `bid.submitted` (seal hash, never prices) · evaluation `technical.opened/completed`, `conflict.declared`, `score.recorded/moderated`, `exclusion.loaded` · awards `award.recommended/decision/approved` (→ `contracts.draftFromAward`) · contracts `contract.drafted` · payables `contract.terms_set`, `ipc.staged/validation_failed/withdrawn`, `invoice.created/approved/rejected/held/released/accounted`, `period.closed`, `journals.transferred` · insight `insight.generated/failed` (kind, model, inputHash; never the key).

## Conventions
Money AED, 2dp, rounded per line; FX = AED per unit. Dates ISO strings; read time only via `p.today`/`p.clock()`. Errors: `throw new Error('<sentence an end user can act on>')`, returned as is. IDs `p.id('PREFIX')` → `PREFIX-0001`; commands are verbs, events `entity.past_tense`. Sample data is fictional: no real company, client or vendor names.

## Design principles (web/, mandatory; they override any skill's taste rules)
1. **Visual hierarchy**: what is this, what state, what next. One focal point per screen.
2. **Prominent actions**: next step is a high-contrast primary button visible without scrolling, one per region; secondary quieter; destructive looks different and asks for a reason.
3. **Actions come from the engine** (`actions` → `available()`); a blocked action shows the engine's error as the reason.
4. **One type superfamily, IBM Plex** (self-hosted `@fontsource`): Sans UI/body (headings SemiBold, tight tracking), Sans Condensed dense tables, Mono IDs/codes/hashes, Serif only generated documents, Sans Arabic. Tabular figures. Measurable rules: `.claude/agents/frontend-engineer.md` (qa-reviewer enforces).

## Multi-agent operating model
The main session is the **lead architect**: talks to the user, writes specs, owns `core/`, `modules/index.ts`, `CLAUDE.md`, `README.md`, and spawns, reviews and merges. Agents (`.claude/agents/`): domain-engineer (one per capability, owns `modules/<x>.ts` and its test), platform-engineer (`server/`, `db/`, storage/bus, CI, integrations), frontend-engineer (`web/`), qa-reviewer (read-only, one per merge).
Recipe for a capability: (1) lead writes a spec of at most 20 lines (capability, commands, tables, events, controls, acceptance checks, files owned); (2) spawn builders, in parallel when independent (kernel or shared-type changes go through the lead; the core repo is outside this checkout, so builders work there on their own branch); (3) qa-reviewer checks, the lead verifies tests and merges only on the user's go-ahead; (4) lead updates this file. Don't spawn for a change the lead can make in a few edits. Parallel agents share the scratchpad: each uses its own subfolder and ports. Never commit a shared-package change to `main` without the user's go-ahead.
